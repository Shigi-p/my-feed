# PR レビュー観点（草案）

ステータス: **草案**。並行トラック PR（T-Src / T-Score / T-Md / T-Web / T-Store）の事前レビューで出た論点を一般化したもの。
具体バグ票ではなく、次回以降も使えるチェックの型として育てる。

---

## 1. この文書の使い方

- PR を読む前に、該当する節だけ目を通す
- 「全部必須」ではなく、**その PR の性質に効くもの**を選ぶ
- 指摘は可能なら「現象 → なぜ痛いか → 提案（必須 / 任意）」の形にする

---

## 2. 普遍的に使える観点

どのリポジトリでも効きやすい型。

### 2.1 境界と責任

- この変更は **どの層の責任**か（取得 / 計算 / 表示 / 永続化）が明確か
- 隣の層の仕事を取り込んでいないか（例: 表示層が永続化の ID 解決を副作用でやる）
- 「設定に書いた値」と「実行時に効く値」が一致しているか

### 2.2 契約と実装のズレ

- インターフェース（型・Protocol・列名・ステータス）の意味が、実装とドキュメントで一致しているか
- 名前が同じでも中身が違うこと（例: `top_n` 列が実際は返却件数）がないか
- 失敗時の約束（例外を上げる / 空を返す / 部分成功）が一貫しているか
- **Protocol / 抽象クラスの docstring と実装の数値的制約の一致**:
  - 戻り値の型だけでなく、コメントに書かれた期待値（文字数・範囲・形式）も契約の一部
  - 例: Protocol で「150-200文字」と書いているのに、実装で「300-500文字」生成
  - 将来的に複数実装が生まれる場合、期待値のズレは UX の不一致につながる
  - チェック: Protocol の docstring と実装の実際の振る舞い（プロンプト・制約）を照合

### 2.3 結合で初めて壊れるもの

単体テストが緑でも、後から他モジュールと繋ぐと効く点。

- 設定・レジストリ・DI が **実際に配線されているか**（読めるだけで使われない、を疑う）
- キー名の暗黙契約（`score_breakdown` のフィールド名など）が他 PR と揃うか
- 同じ関心の二重処理（例: 取得時と出力時の両方で HTML 除去）で意味が変わらないか
- ライフサイクル（接続・キャッシュ・シングルトン）を次の利用者が安全に使えるか

### 2.4 外部世界との接点

- 非公式 API / HTML スクレイピングの脆さと代替手段が分かるか
- レート制限・タイムアウト・部分障害時に、全体が落ちすぎないか
- テストがフィクスチャ固定すぎて、本番の形の変化を検知できない／逆に脆すぎないか

**外部 API 統合時のチェックリスト**:

新規に外部 API（LLM、データ取得サービス等）を統合する場合、以下を確認：

- **タイムアウト設定**: API クライアントにタイムアウトが設定されているか（推奨: 10-30秒）
  - 無限待機でパイプライン全体が停止しないか
  - URL 取得を含む場合は長めに設定（例: URL Context は 30秒）

- **レート制限対応**: 429 エラーや quota exceeded を検出し、適切に処理しているか
  - 失敗させるだけか、exponential backoff でリトライするか、設計を明示
  - レート制限の上限（RPM / QPM / 無料枠）がドキュメント化されているか
  - Top N の数 × ソース数が制限を超えないか確認

- **部分失敗の許容**: 1 件の API 呼び出し失敗が、全体のパイプラインを止めないか
  - `return None` で継続 vs `raise` で中断、どちらかを明示
  - 全件失敗と部分失敗の区別がログ・ステータスで分かるか

- **エラーメッセージの有用性**: API キー未設定時など、ユーザーが次に何をすべきか分かるか
  - 「〇〇が設定されていません」だけでなく、「.env ファイルに設定」など具体的な手順を含む

- **コスト見積もり**: 有料 API の場合、想定コストが計画書 / README に記載されているか
  - 1リクエストあたりのコスト × 想定実行回数を明示

### 2.5 データ同一性

- 再取得しても安定して同一とみなせる ID か
- お気に入り・履歴など「後で参照するデータ」が、ID 変更で切れないか
- タイムゾーン（naive / aware）の扱いが一貫しているか

### 2.6 運用・マージ

- 同じファイルを複数 PR が触っていないか（衝突コスト）
- lock ファイルや生成物の動かし方が大きすぎないか
- デフォルト設定が「安全側」か「便利側」か、意図が README / config から読めるか

### 2.7 ローカル前提の UI / 個人ツール

- 認証なし・CSRF なしをどこまで許容するかが明示されているか
- 同期処理の待ち時間が体験を壊さないか（連打・二重送信）
- 読み取り操作が書き込み副作用を持っていないか

### 2.8 リファクタリング時の属性・パラメータ保全

リファクタリングやコード整理時に発生しやすいバグを防ぐ。

- **クラス変数 vs インスタンス変数の一貫性**:
  - クラス変数（`_CONSTANT`）を定義してインスタンス変数（`self._constant`）で参照していないか
  - 逆にインスタンス変数として定義したものをクラス変数として参照していないか
  - Python は `AttributeError` を出すが、テストなしでは気づけない

- **設定パラメータの消失**:
  - 関数/メソッドのシグネチャ変更時に、既存のパラメータ（特に `thinking_config` などネストした設定）が「静かに削除」されていないか
  - 削除が必要な場合は明示的に理由を説明し、影響範囲を確認する

- **テストの実行必須**:
  - リファクタリング後は **必ず関連テストを実行** する
  - モック/フィクスチャだけでなく、実際のクラスインスタンス化をテストする
  - テストが緑にならない状態で PR を出さない

**チェック方法:**

```bash
# リファクタリング後、必ず実行
pytest tests/ -v

# 属性エラーが出た場合は定義と参照を照合
rg "self\._[a-z_]+" src/  # インスタンス変数の参照
rg "^\s+_[A-Z_]+ =" src/  # クラス変数の定義
```

### 2.9 エラーハンドリングと診断性

エラー発生時に原因を迅速に特定できるか。

- **エラー詳細の記録**:
  - 例外キャッチ時に最低限 `{type(exc).__name__}: {exc}` を記録しているか
  - 必要に応じて `exc_info=True` または `logger.exception()` でスタックトレースを出力しているか
  - ユーザーに伝わらない「silent failure」（ログだけで続行）になっていないか

- **エラー伝播の一貫性**:
  - パイプライン処理など部分的失敗を許容する場合を除き、例外は適切に上位層へ伝播させているか
  - エラーを握りつぶす場合、その理由がコメントまたはドキュメントに明記されているか

**良い例:**

```python
except Exception as exc:
    logger.warning(
        f"Failed to process {item.id}: {type(exc).__name__}: {exc}",
        exc_info=True  # スタックトレース付き
    )
```

**悪い例:**

```python
except Exception:
    logger.warning("Failed")  # 何が起きたか不明、デバッグ不能
```

### 2.10 コードの衛生（デッドコード・未使用関数）

リファクタリングや実装中に作成した補助関数が、最終的に使われていない場合の検出。

- **定義されているが呼び出されていない関数**:
  - IDE / linter（Ruff の `F401`, `F841`）でも検出可能だが、private 関数（`_func`）は見逃しやすい
  - 特にヘルパー関数やマスキング処理など「デバッグ用に定義したが結局使わなかった」ものが残りやすい

- **判断基準**:
  - 将来的に使う予定がある → コメントで明示（例: `# Used for debug logging when LOG_LEVEL=DEBUG`）
  - 使わない → 削除してコードをシンプルに保つ
  - テスト専用ヘルパー → `tests/` 配下またはテストファイル内に移動

**チェック方法**:

```bash
# 定義されている private 関数を列挙
rg "^def _[a-z_]+\(" src/ --type py

# 各関数が実際に呼び出されているか確認
rg "_function_name\(" src/ --type py
```

## 3. このプロジェクト特有の観点

my-feed（契約ハブ + 並行トラック）で特に効く型。

### 3.1 契約ハブを壊していないか

- `models.py` / 各 `base.py` の意味を、機能 PR が静かに変えていないか
- 変える必要があるなら **契約変更を先出し**できているか
- Fake 実装を残す／消す判断が、その変更の意図と合うか

### 3.1.1 ファイル命名（`base.py`）

- 各パッケージの **`base.py` は Protocol / 契約のみ**（`sources` / `scoring` と同型）
- 実装は役割名のファイルへ置く（例: `output/markdown.py`, `store/memory.py`, `store/sqlite.py`, `sources/zenn.py`）
- スタブを `base.py` に同居させると、後続トラックが実装をそこに足してしまいやすい
- `output` / `store` の実装は `markdown.py` / `memory.py` など役割名のファイルへ。`base.py` に戻さない

### 3.2 トラック単体完了 ≠ プロダクト完成

各トラック PR は「その能力が契約に対して足りるか」で見る。次は別マイルストーンの仕事、と切り分ける。

| 見るもの | まだ見ないもの（例） |
|----------|----------------------|
| T-Src: Item 正規化・障害隔離 | Top 10 の体感品質 |
| T-Score: 正規化の公平性・設定配線 | Web からの戦略 UX |
| T-Md: 貼り付けやすさ・内訳キー | Drive 連携 |
| T-Web: DI・導線・Fake での完走 | 実ソース必須 |
| T-Store: 契約充足・永続の正しさ | UI の見た目 |

### 3.3 並行 PR の読み方

- **衝突ファイル**（`config.toml` / `README` / `cli.py` / `pyproject.toml` / `uv.lock` 等）は、機能より先にマージ戦略を意識する
- 暗黙のクロス契約（metrics キー名、score_breakdown、Item.id 規則）は、片方の PR だけでは検証しきれない
- 「テスト件数」はブランチごとにベースが同じでも、他トラック未マージなので比較しすぎない

### 3.4 スコアとソースの公平性（ドメイン）

- 生のいいね数・星の数をソース横断で比べていないか（禁止方針）
- ソース内件数 1 のときの正規化（例: minmax → 1.0）が、横断ランキングを歪めないか
- metrics が無いソース（GIGAZINE 等）の中立値が、意図どおりか

### 3.5 外部ソース方針

- RSS / 公式 API を捨てて非公式手段を選ぶ場合、理由が notes に残っているか
- GitHub Trending など壊れやすい部品が **モジュール隔離**されているか
- デフォルトが offline-safe（`fake`）のままか、実ソース有効化の手順が書いてあるか

### 3.6 M1 / M2 合流前のチェック（短く）

マイルストーン PR ではトラック PR と違う問いになる。

- Fake がデフォルト経路から外れているか
- 設定・スコアラー・レンダラ・Store が **同じ実行経路で配線**されているか
- partial 失敗（`source_errors`）が CLI / Web の両方で見えるか

## 4. レビューコメントの書き方（短例）

```text
【観点】設定と実行の一致
【観察】config に half_life があるが、戦略生成時に渡していないように見える
【影響】運用でパラメータを変えても順位が変わらない
【提案】get_scorer 時に AppConfig から注入 / または「未配線」を docs に明示（必須）
```

指摘の強さ:

- **必須**: 契約違反、データ破壊、設定が効かない、結合で確実に困る
- **推奨**: 後で直せるが今決めた方が安い
- **任意**: 味・文言・将来の最適化
