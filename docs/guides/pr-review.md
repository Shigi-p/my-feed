# PR レビュー観点

PR を読むときのチェックの型。全部必須ではなく、その PR の性質に効くものだけ選ぶ。
指摘は可能なら「現象 → なぜ痛いか → 提案（必須 / 任意）」の形にする。

---

## 1. 境界と責任

- この変更はどの層の責任か（取得 / スコア / 表示 / 永続化 / 要約）が明確か
- 隣の層の仕事を取り込んでいないか
- 設定に書いた値と実行時に効く値が一致しているか

## 2. 契約と実装

- `models.py` / 各 `base.py` の意味を、機能 PR が静かに変えていないか
- 変える必要があるなら契約変更を先出しできているか
- 名前が同じでも中身が違うことがないか（例: `top_n` 列が実際は返却件数）
- 失敗時の約束（例外 / 空 / 部分成功 / `None`）が一貫しているか
- Protocol の docstring に書いた数値制約と実装が一致しているか

## 3. 結合で壊れるもの

- 設定・レジストリ・DI が実際に配線されているか
- 暗黙のキー名（`metrics` / `score_breakdown` など）が他モジュールと揃うか
- 同じ関心の二重処理で意味が変わっていないか
- 読み取り操作が書き込み副作用を持っていないか

## 4. 外部世界

- 非公式 API / HTML スクレイピングの脆さと代替が分かるか
- 壊れやすい部品がモジュール隔離されているか
- タイムアウト・レート制限・部分障害でパイプライン全体が落ちすぎないか
- API キー未設定など、次に何をすべきかメッセージから分かるか
- 有料 API なら想定コストが分かるか

## 5. ドメイン

- 生のいいね数・星の数をソース横断で比べていないか
- metrics が無いソースの中立値が意図どおりか
- 再取得しても安定する ID か。お気に入りが ID 変更で切れないか
- ルート `config.toml` が offline-safe（`fake`）のままか

## 6. リファクタと衛生

- シグネチャやネスト設定が静かに消えていないか
- 定義だけ残った未使用関数を消しているか
- 関連テストを実行しているか

## 7. 指摘の強さ

- **必須**: 契約違反、データ破壊、設定が効かない、結合で確実に困る
- **推奨**: 後で直せるが今決めた方が安い
- **任意**: 味・文言・将来の最適化

```text
【観点】設定と実行の一致
【観察】config に half_life があるが、戦略生成時に渡していないように見える
【影響】運用でパラメータを変えても順位が変わらない
【提案】build_scorer 時に AppConfig から注入（必須）
```
