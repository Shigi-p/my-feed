# 協働・方針メモ（エージェント向け）

ステータス: **草案**。会話と明示指示から抽出した「大切にしていること」。  
方針が変わったら、このファイルを直すか、日付付きの追記で上書き判断を残す。

対象: このリポジトリでエージェント（や人）と進めるときの前提。

---

## 1. 進め方

- **計画 → 承認 → 実装**の順を崩さない。いきなりコードを出さない。
- 全体計画を先に示し、「実装してください」と言ったあとだけ、**小さいステップ**で進める。
- **判断が必要なときだけ聞く。** 機械的な修正・コメント追加は任せ、方針・トレードオフ・意図が分かれる点だけ確認する。
- **承認ポイントを意図的に置く。** 計画 PR、契約ハブ（C0）、トラック単位など、「ここで一度見てほしい」を文書とチェックリストで残す。

## 2. 学習・コミュニケーション

- **コードより理由。** 生成物そのものより、「なぜこの形か」「別案との差」を優先する。学習用の協働を前提にする。
- **日本語で、短く、事実ベース。** 相槌や過剰な褒めは不要。結論と根拠を先に、長文化しない。
- **方針の変更は履歴として残す。** 旧メモを消して上書きせず、日付付きで「なぜ変えたか」を堆積する（`docs/plans` の運用と同じ姿勢）。

## 3. 設計・実装

- **契約（境界・署名）を先に固定する。** 実装の中身よりモジュール間の約束事を先に決め、Fake で並行開発できるようにする。
- **Fake を見える形で残す。** UI やパイプラインを本実装待ちにせず進め、マイルストーンの意図に合うなら Fake を消さない判断も取る。
- **無料・ローカル・最小から。** AI 要約などは後回し。まず一覧・保存・お気に入りなど、手元で動く価値を先に取る。
- **拡張は設定と差し替えで。** スコアリング複数・ソース追加など、「配線を変えれば差し替えられる」形を好む。ソース横断で生のいいね数を直接比較しない、といった禁止方針も明示する。
- **ツールは段階的に。** いまは uv 中心で足りるならそれでよく、Docker などは必要になってから。短期の摩擦と長期の運用を分けて考える。

## 4. レビュー・品質

- **レビューはコメントとして残し、観点は一般化する。** 一度きりの指摘で終わらせず、繰り返し出る論点をガイドに落とす（例: [pr-review.md](./pr-review.md)）。
- **契約と実装のズレ・命名・責務の置き場を気にする。** Protocol 専用の `base.py` に実装を同居させない、役割名のファイルに置く、など後続が迷わない構造を重視する。
- **マージ順を設計する。** 依存の薄い／基盤になるものから入れ、コンフリクトは意図を保ったまま解消する。

## 5. このプロダクトで特に意識すること

- **オンデマンド**で取りに行き、結果をアーカイブ・お気に入りできること
- **横断 Top 10**のような「選ばれた短いリスト」であること（全部読みではなくキュレーション）
- **Web（モバイル）＋ Markdown**で、後段の思考ツールに渡しやすいこと
- 認証や重いインフラより、**まずローカルで完結する体験**

## 6. 一文での要約

> 先に契約と計画を共有し、承認した範囲だけ小さく実装する。コードの量より「なぜ」を残し、判断以外は任せ、無料・ローカル・差し替え可能な形で、学習しながら並行に進めたい。
