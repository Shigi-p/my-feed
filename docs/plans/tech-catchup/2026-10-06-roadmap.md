# my feed — 初回ロードマップ

- 作成日: 2026-10-06
- ステータス: 計画確定（実装未着手）
- 進め方: **B → A**（先に CLI で取得パイプラインを固め、続いてローカル Web）

---

## 1. 目的

技術記事と GitHub Trending に効率よく触れ、気になったものを自分で読みつつ、Gemini などで壁打ちできる状態をつくる。

**やること**

- 任意タイミングで情報を取得し、横断評価で **厳選 10 件** にする
- スマホでも見られる一覧（最終的に Web）と、壁打ち用 **Markdown** を出す
- 履歴・お気に入りであとから見返せる

**やらないこと（当面）**

- AI 要約（有料・無料枠とも後回し。ルールベース抜粋まで）
- Google Drive 連携
- 本番公開・本格認証
- 既読除外

---

## 2. 要件サマリ

| 項目 | 決定内容 |
|------|----------|
| 情報源 | Zenn / Qiita / GIGAZINE / GitHub Trending（言語不問） |
| 興味領域 | 広め。GIGAZINE は当面フィルタなし |
| 件数 | 合計 10 件（厳選） |
| 選別 | **横断ランキング**（ソース固定配分ではない） |
| 評価 | **複数のスコアラーを差し替え可能**（基準は後から変更する） |
| トリガー | Web ボタン（主）。最初はローカル。Actions は副経路として後続候補 |
| 閲覧 | デバイス非依存の Web（本番は後）。マイルストーンはローカル動作 |
| 壁打ち | ChatGPT / Gemini に貼る Markdown。Drive は後回し、まずファイル DL |
| 履歴 | 実行履歴 + お気に入り（アーカイブ） |
| 認証 | 必要だが面倒なので **ローカル完走を先**に置く |
| コスト | できるだけ無料。要約は後検討 |
| 拡張性 | ソース追加・評価基準変更が容易であること |

### 各アイテムに含める情報

- タイトル / URL / 出典
- 1〜3 行の抜粋（ルールベース）
- タグ・分野（取れる範囲）
- 「なぜ今見る価値があるか」（ルール or テンプレ文）
- 関連アイデア・学習の問い（壁打ち用の定型プロンプト要素）
- Gemini 等に貼れる Markdown 断片

## 3. アーキテクチャ方針

変更容易さを最優先し、**取得・評価・出力**を分離する。

```
[Source Adapter × N]  →  共通 Item[]
         ↓
[Score Strategy × M]  →  Top 10
         ↓
[Outputs: CLI / Markdown / Web / Favorite Store]
```

### 3.1 Source Adapter

- ソースごとに 1 モジュール
- 責務: 外部取得 → **共通 Item** へ正規化
- 追加・削除・無効化はアダプタと設定だけで完結させる
- 取得手段は **公式 RSS / 公開フィード優先**（壊れにくさ優先）
- GitHub Trending は公式が弱い想定 → **いちばん壊れやすい部品として隔離**

### 3.2 共通 Item（初期案）

実装時にフィールドは調整してよいが、最低限これで揃える。

| フィールド | 説明 |
|------------|------|
| `id` | 安定 ID（出典 + 元 ID or URL ハッシュ） |
| `source` | `zenn` / `qiita` / `gigazine` / `github_trending` |
| `title` | タイトル |
| `url` | 本文 or リポジトリ URL |
| `published_at` | 公開・更新時刻（取れる範囲） |
| `excerpt` | 短い抜粋 |
| `tags` | タグ配列 |
| `metrics` | ソース固有の人気指標（likes, stocks, stars 等） |
| `raw` | デバッグ用の生データ（永続化は任意） |

### 3.3 Score Strategy

- インターフェースを先に決め、実装を差し替え可能にする
- 初期候補:
  - `popularity` — ソース内で正規化した人気指標
  - `recency` — 新しさ加点
  - `hybrid`（デフォルト候補）— 正規化人気 × 新しさ減衰
- **生のいいね数での横断比較はしない**（ソース内ランク / パーセンタイル等に正規化してから横断）
- 実行時にどの戦略を使うか選べるようにする（CLI フラグ → 後に Web）

### 3.4 出力

- CLI: 取得結果・Top 10 の確認
- Markdown: 10 件まとめ + 1 件テンプレ
- Web: 一覧・取得ボタン・履歴・お気に入り・DL
- Store: SQLite（実行履歴・お気に入り）

### 3.5 技術スタック（仮決め）

| 層 | 選択 | 理由 |
|----|------|------|
| 言語 / API | Python + FastAPI | RSS・取得処理のしやすさ、単一プロセスで Web 化しやすい |
| DB | SQLite | ローカル完走・認証なしでも履歴が残る |
| フロント | 薄いサーバサイドテンプレ or 最小 HTML | 最初は一覧特化。カード過多にしない |
| パッケージ管理 | リポジトリ慣例に合わせる（未定なら `uv` or `pip`） | 後続メモで確定 |
| デプロイ | Phase 5 まで考えない | ローカル優先 |

## 4. Web トリガー vs GitHub Actions

| 観点 | Web | Actions |
|------|-----|---------|
| 任意タイミング | URL を開いて即実行しやすい | スマホから Actions UI が重い |
| 体験の一体感 | 取得〜一覧〜お気に入り〜 MD DL が同じ場所 | 取得と閲覧が分かれやすい |
| フィードバック | 進捗・失敗を画面で見せやすい | ログ確認になりがち |
| 永続化 | DB と自然につながる | 別設計が必要になりやすい |

**方針**: 主トリガーは Web。Actions は定期バックアップや定期取得の副経路として Phase 5 以降の候補。

### Phase 1 — CLI で取得パイプラインを固める（B）

**ゴール**: ターミナルから 1 コマンドで、4 ソース取得 → スコア → Top 10 が再現可能に出る。

#### タスク分解

1. **リポジトリ骨格**
   - アプリディレクトリ構成（例: `src/` or `app/`）
   - 依存関係・実行方法を README に短く書く
   - 設定の置き場（有効ソース、選件数、デフォルトスコアラー）

2. **共通モデル**
   - `Item` 型 / dataclass / pydantic モデル
   - ソース名の列挙
   - ID 生成ルール

3. **Source Adapter 枠**
   - 共通インターフェース（`fetch() -> list[Item]`）
   - エラー時の方針（1 ソース失敗でも他は継続、ログに残す）

4. **アダプタ実装（個別）**
   - Zenn
   - Qiita
   - GIGAZINE
   - GitHub Trending（隔離・失敗しても他ソースで 10 件を目指せるフォールバック）

5. **Score Strategy 枠**
   - 共通インターフェース（`score(items) -> ranked`）
   - ソース内正規化ヘルパ
   - `popularity` / `recency` / `hybrid` の最低限実装
   - CLI から戦略名を指定可能に

6. **パイプライン CLI**
   - `fetch → score → top N` を一本化
   - 結果を stdout（表 or JSON）で確認
   - （任意）結果 JSON をファイル出力

7. **手動確認**
   - 各ソースが空でないこと
   - Top 10 が安定して出ること
   - 1 ソース障害時の挙動確認

**完了条件**

- ローカルで 1 コマンド実行 → Top 10 が表示される
- スコアラーをフラグで切り替えられる
- ソース追加が「アダプタ 1 つ + 登録」で済む形になっている

**まだやらない**

- Web UI、Markdown 本格テンプレ、SQLite、お気に入り

### Phase 2 — Markdown と一覧体裁

**ゴール**: Top 10 を Gemini に貼って壁打ちできる Markdown が出せる。

#### タスク分解

1. 抜粋生成（説明文・RSS summary 等からルールベースで 1〜3 行）
2. 「見る価値」一文のテンプレ（スコア内訳や出典・新しさに基づく単純文で可）
3. 壁打ち用の問い・アイデアの定型ブロック
4. **10 件まとめ Markdown** 出力
5. **1 件分テンプレ** 出力（気になったものだけコピーしやすい形）
6. CLI から `.md` ファイル書き出し

**完了条件**: 生成 Markdown を Gemini に貼り、壁打ちに使える

### Phase 3 — ローカル Web（A）+ 履歴・お気に入り

## 7. リスクと対策

| リスク | 対策 |
|--------|------|
| ソース仕様変更で取得が壊れる | アダプタ隔離、RSS 優先、1 ソース失敗でも継続 |
| GitHub Trending が特に脆い | 単独モジュール化、失敗時は他ソースのみで Top 10 |
| 人気指標のスケールがソース間で違う | ソース内正規化してから横断 |
| 厳選 10 件の質が低い | スコアラーを複数持ち、運用で切替・改善 |
| 範囲が広がって進まない | Phase 1 完了まで Web/DB/AI/Drive に手を出さない |
| GIGAZINE がノイズになる | 当面無フィルタで運用し、Phase 4 で設定化 |
