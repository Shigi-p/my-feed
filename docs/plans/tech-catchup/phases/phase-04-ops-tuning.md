# Phase 4 — 運用改善・設定化

| 項目 | 内容 |
|------|------|
| ステータス | 計画承認待ち |
| 依存 | Phase 3 をしばらく使ってみてからの着手を推奨 |
| 後続 | Phase 5（必要なら） |
| ゴール | ソースや評価基準の変更が、コード大改修なしで試せる |

---

## 1. 目的

実運用で見えた摩擦を下げる。  
特に「ソースを足す／消す」「スコアをいじる」「失敗が見えない」を改善する。

Phase 1〜3 で作った境界（Adapter / Strategy / config）を、**運用者向けに露出**する段階。

---

## 2. スコープ

### やること（優先度順）

1. ソースの有効 / 無効を設定（および可能なら UI）で切替
2. スコアラー追加手順の短文化（ドキュメント）
3. 件数・減衰パラメータ等の調整をしやすくする
4. 取得失敗の可視化（どのソースが落ちたか）
5. GIGAZINE 等の任意フィルタを **設定で** 有効化できるようにする（デフォルトはオフのまま）

### やらないこと

- 本番認証・公開（Phase 5）
- LLM 要約本導入（Phase 5）
- Drive 連携（Phase 5）
- スコアラーの自動学習や個人化レコメンド

---

## 3. 設定項目の拡張案

`config.toml`（名前は実装に合わせる）へ寄せる例:

```toml
top_n = 10
default_scorer = "hybrid"

[sources.zenn]
enabled = true

[sources.qiita]
enabled = true

[sources.gigazine]
enabled = true
# Phase 4 で追加する任意オプション
keyword_filter_enabled = false
keyword_allowlist = []

[sources.github_trending]
enabled = true

[scoring.hybrid]
recency_half_life_hours = 36
neutral_popularity_when_missing = 0.5
```

UI から全部いじる必要はない。まずファイル、次に Web の簡易トグル、の順が安全。

---

## 4. 失敗の可視化

Phase 3 の `source_errors` を UI に出す。

- 実行結果ページ上部に警告: 「GIGAZINE: timeout」等
- `status=partial` を履歴一覧で分かるようにする
- CLI でも同様の警告を stderr へ（未整備ならここで揃える）

---

## 5. スコアラー追加手順（ドキュメント成果物）

`docs/plans/tech-catchup/` ではなく、実装寄りに置くなら:

- `docs/guides/add-scorer.md`（推奨）
- または README の短い節

含める手順:

1. `scoring/foo.py` を追加
2. レジストリ登録
3. 設定にデフォルトパラメータ
4. テスト 1 本
5. CLI / Web の選択肢に出ること

ソース追加も同様に `docs/guides/add-source.md` を作ると Phase 1 の設計意図が運用に残る。

---

## 6. 任意フィルタ（GIGAZINE）

合意どおりデフォルトは無フィルタ。Phase 4 で「いつでもオンにできる口」だけ用意する。

初期案:

- タイトル部分一致の allowlist / blocklist
- 設定オフ時は現状どおり全件候補

質の議論は設定値の調整で行い、コード分岐を増やしすぎない。

## 7. タスク分解

### T1. 設定の正式化

- [ ] ソース/スコアパラメータを設定ファイルへ集約
- [ ] 読み込みバリデーション（未知キーは警告）

- [ ] Web / CLI 双方
- **完了**: partial 失敗が一目で分かる

### T4. ガイドドキュメント

- [ ] add-source / add-scorer
- **完了**: 手順どおりにダミー実装を足せる

### T5. フィルタ口（デフォルトオフ）

- [ ] GIGAZINE キーワードフィルタ設定
- **完了**: オフ時挙動不変、オン時のみ絞り込める

### T6. （任意）取得 UX

- [ ] 長時間取得のスピナー / タイムアウトメッセージ改善
- [ ] バックグラウンド実行が必要ならここで設計判断
